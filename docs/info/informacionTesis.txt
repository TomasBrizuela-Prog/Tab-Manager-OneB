Fase 0 — Setup y decisiones de arranque
Stack elegido: C#/.NET (WPF) para contenedor + core Win32, por P/Invoke de primera clase. Plugins en su terreno nativo (IntelliJ en JVM, VS Code en TypeScript). Core del reparenting es territorio del autor; el resto se delega a Claude.
Estructura: solución con cuatro proyectos — OneBlack.Contenedor (WPF), OneBlack.Core (Win32, del autor), OneBlack.Core.Tests (NUnit), OneBlack.Janitor (consola, watchdog). .NET 10, Visual Studio Community 2026.
Repo: git desde el día uno, remoto en GitHub personal privado; repo de facultad se sumará después como segundo remoto.
Método: spike antes que arquitectura; Claude entrega clases completas comentadas, el autor lee/valida/hace explain-back corto.
Fase 1 — Spike de reparenting (validación de la incógnita central)
Pregunta que abría el proyecto: ¿es posible embeber un IDE real en una ventana propia? Respondida: SÍ. Go/no-go = GO.
Modelo mental WPF clave: WPF dibuja sus controles en vez de crearlos como ventanas del sistema, así que no hay un HWND-hijo donde hospedar una ventana externa; HwndHost crea esa ventana real faltante y ahí se reparenta.
Clases del core construidas: VentanaAnfitriona : HwndHost (puente WPF↔Win32), AdoptadorDeVentanas (el músculo, maneja varias ventanas vía diccionario), EstadoOriginalVentana (guardar antes de tocar, restaurar al soltar).
Descubierto — el delegate del wndProc debe guardarse en un campo para que el GC no lo recolecte mientras Windows lo usa (bug clásico si se omite).
Descubierto — fondo sólido en la clase de ventana (hbrBackground negro) resuelve el "fantasma" que quedaba al devolver: el contenedor no se repintaba solo.
Secuencia de adopción (orden no casual): guardar estado → cambiar estilos (quitar WS_POPUP/WS_CAPTION/WS_THICKFRAME, poner WS_CHILD) → SetParent → SetWindowPos para encajar → registrar → persistir. Devolver es la inversa.
Validado con Notepad clásico: adopta (desaparece de la barra de tareas = reparenting genuino), sincroniza resize, devuelve intacto.
Fase 2 — Janitor / supervivencia ante crash
Construido: PersistenciaEstado (archivo ventanas-adoptadas.json con escritura atómica por temporal+renombre) y OneBlack.Janitor (proceso separado que duerme con WaitForSingleObject hasta que OneBlack muera y restaura las ventanas).
HALLAZGO CRÍTICO — el janitor reactivo pierde la carrera contra la muerte dura. Con kill duro (TerminateProcess), la ventana hija (WS_CHILD) muere en el mismo instante que OneBlack. El janitor llega rapidísimo pero después de que la ventana ya murió. Motivó el rediseño completo de la estrategia de supervivencia.
Restricción de fondo confirmada (Microsoft): una ventana tiene parent O owner, nunca ambos. WS_CHILD da confinamiento visual pero muere con el padre; owner da supervivencia pero no confina. No hay flag que dé las dos.
DECISIÓN CERRADA: priorizar confinamiento visual (WS_CHILD, es la identidad del producto) y garantizar no-pérdida de trabajo por persistencia de sesión, no por supervivencia de ventana. El insight: el objetivo correcto no es "que la ventana sobreviva" sino "que el trabajo del usuario sobreviva" (se reconstruye desde disco). Tres capas: cierre ordenado (hecho), manotazo por excepción (hecho pero frágil, no principal), persistencia de sesión (diseñada, pendiente de implementar).
Fase 3 — Enumeración, whitelist y adaptadores
Se pasó de FindWindow a EnumWindows (recorre todas las ventanas y filtra con lógica propia). Motivado por múltiples ventanas del mismo programa y por VS Code (clase de ventana genérica de Chromium Chrome_WidgetWin_1, compartida con Discord/Chrome — no sirve filtrar por clase).
Construido: BuscadorDeVentanas (enumera + filtra por visible/con título/en whitelist, identifica por nombre de proceso) y CatalogoDeProgramas (la whitelist; agregar un programa = una línea).
DECISIÓN — whitelist, no blacklist. Razones: identidad del producto, seguridad (nunca adopta ventanas del sistema por accidente), y calidad por programa (cada uno tiene sus mañas; soportar una lista conocida permite afinar y prometer que funciona). Excluye a la propia OneBlack automáticamente.
Fase 4 — Adopción de VS Code (Electron/Chromium)
HALLAZGO — ventana negra tras adoptar. VS Code se adoptaba a nivel Win32 pero no renderizaba (quedaba negro). Causa: la composición por GPU de Chromium — la superficie GPU queda huérfana al reparentar y Chromium no la recrea. Solución: lanzar VS Code con --disable-gpu (renderiza por software, sin superficie GPU que se rompa). Confirmó el modelo "OneBlack lanza los programas" con los flags correctos, en vez de "adoptar lo que el usuario ya abrió".
HALLAZGO — el teclado no llegaba a VS Code. Mouse funcionaba, teclado no. Es el problema más profundo del reparenting cross-proceso. Dos causas: (1) las colas de input de threads distintos se desacoplan al reparentar; (2) Chromium enruta el teclado a su vista interna según WM_ACTIVATE, que el reparenting rompe. Solución combinada: AttachThreadInput (acopla las colas de input; desacoplar SIEMPRE al devolver o rompe el foco de todo el sistema) + SendMessage(WM_ACTIVATE, WA_CLICKACTIVE) (despierta el enrutamiento interno de Chromium). Esta segunda pieza era la que faltaba.
Fase 5 — Selección de candidatas (UI) y correcciones del ciclo
UI de selección con ComboBox (Refrescar + Adoptar + Devolver) reemplazó los botones de prueba.
Corregido — cambio de pestaña: MostrarSolo(hwnd) muestra la elegida y oculta el resto (SW_SHOW/SW_HIDE).
Corregido — Devolver dejaba la ventana oculta: SW_SHOW al inicio de Devolver.
Corregido — refrescar rompía la adoptada: las adoptadas no aparecen en la enumeración (son hijas); se combinan libres + adoptadas recordadas preservando selección.
Corregido — escalado DPI (125%): WPF trabaja en unidades lógicas, Win32 en píxeles físicos. Helper DimensionesFisicas() multiplica por el factor de escala. Debe funcionar CON escalado, no pedir desactivarlo.
Fase 6 — Estabilización del ciclo adoptar/devolver (sesión más reciente)
RESUELTO — condición de carrera adoptar/devolver. Síntoma: adoptar+devolver rápido rompía; esperar unos segundos lo evitaba. Causa: los Dispatcher.BeginInvoke(Render) diferidos corrían después del Devolver, sobre una ventana ya restaurada. Intento fallido: reemplazar por UpdateLayout() síncrono (mató la carrera pero rompió el encaje). Solución: guardar la operación diferida en un campo (encajeDiferido) y cancelarla con .Abort() al inicio del Devolver si sigue pendiente.
RESUELTO — render negro en Chromium tras mostrar/adoptar. Dato clave: clickear o cambiar de pestaña no lo revivía. Causa: Chromium solo recompone su superficie ante WM_SIZE, no ante SW_SHOW ni WM_ACTIVATE. Solución: ForzarRepintado(hwnd) — latigazo de tamaño (1px y volver) + RedrawWindow con RDW_ALLCHILDREN. Se dispara en MostrarSolo y con reintentos espaciados (timer, 3×~120ms) tras adoptar. Race-safe.
HIPÓTESIS DESCARTADA — corrupción de WS_CHILD. Se creyó que WS_CHILD se propagaba entre ciclos. El fix (& ~WS_CHILD) empeoró el bug. Se instrumentó con logs de estilos en hex: probaron que los estilos se restauraban perfectos. Hipótesis falsa. Aprendizaje de método: instrumentar antes de teorizar; el fix a ciegas costó tiempo.
IDENTIFICADO — recreación espontánea del HWND (la causa real del "aleatorio"). Los logs mostraron el HWND del Notepad cambiando entre pruebas (2060C→30602). El Notepad de Windows 11 (WinUI) destruye y recrea sus ventanas solo. OneBlack operaba al devolver sobre un handle ya muerto → ventana fantasma. Prueba decisiva: Notepad quieto 30s → rompió igual (espontáneo, no por interacción); VS Code ciclado → siempre sano. Conclusión: no es bug de OneBlack, es un caso de prueba patológico. Los IDEs reales tienen HWND estables.
IMPLEMENTADO — salvaguarda IsWindow. Chequeo defensivo en Adoptar, Devolver (con helper LimpiarAdoptada), MostrarSolo, ReajustarTamaño, ForzarRepintado, DevolverTodas. No cura la recreación (imposible) pero evita operar sobre handles muertos y dejar basura. Aditivo: el camino feliz no cambia.
DECISIÓN — Notepad nuevo fuera del catálogo. Validado como no reparentable de forma confiable. Refuerza que la whitelist también garantiza "programa validado como reparentable", no solo seguridad.
Hallazgos de alcance (transversales, material de tesis)
Firma de código como requisito no-funcional de distribución. Smart App Control (WDAC) bloqueó la carga de OneBlack.Core.dll sin firmar (0x800711C7), de forma no-determinística (por reputación/heurística). Una app de reparenting es indistinguible de malware para los controles de Windows. La firma con certificado de editor verificado (EV, clave en hardware desde 2023) es obligatoria para distribuir a terceros — mismo requisito que productos comerciales como Groupy. Para la tesis: documentar la decisión (ADR) y opcionalmente demostrar el pipeline con certificado autofirmado. DECISIÓN DE FONDO ABIERTA — en análisis.
Identidad de ventanas en Win32 y límite de soportabilidad. El reparenting por HWND asume que el handle es estable durante la adopción; las apps WinUI lo violan recreando ventanas. Conclusión: el soporte de una app debe validarse por su estabilidad de ventana, no asumirse; y la mitigación correcta para el caso patológico es excluirlo y detectar la invalidación con gracia, no re-seguir la ventana. Saber dónde parar de robustecer es criterio de ingeniería.
Las apps modernas (Chromium, WinUI) reaccionan al reparenting de formas que las Win32 clásicas no. Patrón transversal: VS Code necesita --disable-gpu (render) y WM_SIZE (repintado); el Notepad WinUI recrea su HWND. El Notepad clásico (Win32 puro) nunca tuvo ninguno de estos problemas. Cada tecnología de UI tiene su propio conjunto de esquinas filosas.

Hecho:

Se cerró la exploración de diseño en Claude Design. Dirección final: Terminal Neón + calma navegable de Linear. El mockup pasó por tres estados (denso → vacío → estructurado) hasta converger.

Descubierto / aprendido:

La identidad visual necesitaba contención, no menos densidad. El problema no nombrado era falta de estructura (elementos flotando) + falta de columna de identidad. Se resolvió con paneles contenidos + sidebar vertebral, estilo Linear.
Restricción de diseño confirmada como load-bearing: el IDE reparentado pinta encima de su región, así que ningún elemento WPF (ticks, bordes, barras) puede ir sobre el hueco — solo alrededor. Condiciona todo el layout.
El layout nuevo corrió el timing del encaje (el hueco ahora es celda de un Grid con sidebar, tarda un instante más en asentar su ancho). Eso reexpuso el render intermitente de Chromium — las salvaguardas de repintado no alcanzan en el nuevo contexto de timing.

Es un requisito ya documentado ("detectar si un IDE se cerró externamente"). Solución conocida: watcher periódico con IsWindow que limpie handles muertos. Próximo objetivo, acotado y limpio.
Repintado intermitente de Chromium (pulido): negro aleatorio al adoptar en el layout nuevo. Es una carrera de timing conocida. Plan: engancharlo al SizeChanged (cuando el layout está asentado) en vez de a timers que adivinan. Atacar cuando el layout final esté estable.

25/08
Bitácora — Sistema de pestañas, apertura de proyectos y refinamiento visual
Resumen ejecutivo

Sesiones dedicadas a convertir OneBlack de "adopta una ventana" a "gestor multi-ventana con pestañas". Se construyó el sistema de pestañas dinámicas, la apertura real de proyectos vía selector de carpeta, y se resolvieron varios bugs de foco, encaje y ciclo de vida que fueron apareciendo. En paralelo se consolidó la capa visual (chrome Terminal Neón) y se hizo la sidebar plegable. Al cierre, OneBlack ya permite abrir varios proyectos en pestañas, cambiar entre ellos, y las pestañas mueren con su ventana.

Hecho y funcionando

Foco de teclado — resuelto en capas.

Al lanzar OneBlack la ventana él mismo, esta nace sin ser "activada" por el usuario, así que AttachThreadInput no alcanzaba. Se sumó SetForegroundWindow + SetFocus en MostrarSolo para entregar el foco a nivel SO.
Tras notificación del IDE que roba el foco, se recupera solo mediante un timer que reafirma el foco periódicamente (con guarda this.IsActive para no robar foco a otras apps). Se extrajo ReaplicarFoco en el core: versión quirúrgica que reaplica SOLO foco, sin tocar show/hide/encaje/repintado (clave para poder dispararlo seguido sin romper el encaje).

Clavado de ventana (posición) — resuelto pragmáticamente.

La ventana adoptada se desencajaba (arrastrándola desde la topbar custom de Chromium, o por el borde) y se rompía al maximizar. La subclasificación (WM_WINDOWPOSCHANGING) sola no alcanzó porque Chromium mueve su ventana por vías internas no interceptables.
Solución: timer corrector que reencaja en (0,0) cada 200ms vía ReajustarTamaño. Atrapa todas las vías porque corrige el hecho consumado. Decisión de ingeniería consciente: robustez reactiva sobre elegancia preventiva.

Motor de lanzamiento (LanzadorDeProgramas).

OneBlack lanza el programa con sus flags (--disable-gpu) apuntando a una carpeta, hace polling hasta que aparece la ventana, y la adopta. Más rápido y limpio que adoptar lo abierto por el usuario.
CatalogoDeProgramas extendido con ArgumentosBase y UsaCarpeta.

Sistema de pestañas (Opción A — idiomática WPF).

PestañaVentana (modelo con INotifyPropertyChanged), ObservableCollection<PestañaVentana> bindeada a un ItemsControl. Una pestaña por ventana adoptada.
Cambio de pestaña vía MostrarSolo de la elegida. Pestaña Cockpit fija + pestañas de IDE dinámicas + botón "+".
Detección de cierre externo: un chequeo periódico (LimpiarPestañasMuertas + VentanaSigueViva en el core) elimina la pestaña cuando su ventana muere por la X/Alt+F4/crash. Resuelve el pendiente que arrastrábamos: la pestaña ahora muere con su contenido.

Apertura real de proyectos.

El "+"/flujo de apertura abre un selector de carpeta nativo (OpenFolderDialog) y lanza VS Code ahí. Se extrajo LanzarYAgregarPestaña como flujo central reutilizable.
Guarda anti-duplicado: cada pestaña recuerda su carpeta; si intentás abrir una ya abierta, activa la existente en vez de relanzar. Resolvió el bug del lanzamiento colgado que cruzaba nombres de pestañas.

Chrome visual Terminal Neón consolidado.

Layout final: titlebar (pestañas + "+"), sidebar de identidad (logo, navegación de espacios, hub), statusbar fina, hueco enmarcado. Andamiaje del spike (ComboBox/Refrescar/Adoptar/Devolver) removido.
Tokens de color traducidos a recursos WPF en App.xaml.

Sidebar plegable — hecha profesionalmente.

Riel de 56px con íconos al plegar, 212px con texto al desplegar. Al plegar/desplegar, la ventana adoptada se reajusta para llenar el nuevo espacio (plegado "de verdad", no cosmético).
Implementado con Style/ControlTemplate + binding (converter BoolAVisibilityConverter, INotifyPropertyChanged en la Window) en vez de recorrer el árbol visual. Se introdujo infraestructura reusable (converter, notificación) que sirve para el resto de la UI con datos.
Descubierto / aprendido
El foco tiene más capas de las que sabíamos: acople de input (AttachThreadInput) ≠ entrega de foco (SetForegroundWindow+SetFocus). Una ventana lanzada por OneBlack necesita ambas.
Reafirmar el foco muy seguido pelea con los clicks del usuario: el timer a 200ms hacía que los clicks en pestañas "no respondieran". Se separó reencaje (200ms) de refoco (~1s). Balance fino: muy seguido estorba, muy espaciado tarda en recuperar teclado.
Chromium mueve su ventana por vías internas no interceptables desde la top-level. Confirmó (otra vez) que la ventana adoptada es un cascarón y la acción real pasa en ventanas internas de Chromium.
VS Code reusa ventana para una carpeta ya abierta → el lanzador quedaba colgado esperando una ventana nueva que no llegaba, y capturaba la siguiente ventana con la etiqueta vieja. Se resolvió con la guarda anti-duplicado.
Bugs/pendientes abiertos
Botón de desplegar solapado en el riel plegado (visual menor, anotado).
Botones de sidebar deshabilitados cuando no aplican: el trigger visual ya está en el estilo (IsEnabled=False → opacity 0.35); falta conectar la lógica cuando se implemente la navegación.
Página "nueva pestaña" (próximo objetivo grande): que el "+" abra una página base de OneBlack estilo "nueva pestaña de navegador" — apps disponibles para adoptar, selector de carpeta, y a futuro proyectos recientes. Implica arquitectura de área central que alterne entre ventanas adoptadas y páginas propias de OneBlack (ocultando el hueco cuando se muestra una página WPF, por la restricción de que el IDE pinta encima). Desbloquea también el Cockpit.
Persistencia de proyectos (recientes + fijados): archivo JSON local en %LocalAppData%\OneBlack\, sin cuenta ni login (app local single-user, ya decidido). Mismo mecanismo que PersistenciaEstado ya usa.
Lanzamientos simultáneos rápidos podrían cruzarse (caso borde); el fix robusto sería identificar la ventana por PID del proceso lanzado, no por "cualquier ventana nueva". No prioritario.
Arrastrados de antes: detección de cierre externo (RESUELTO esta sesión vía pestañas), adaptar IntelliJ/WebStorm, decisión de firma/distribución (ADR abierto).

27/08
Foco: adaptar IntelliJ IDEA y WebStorm (Java/Swing), el segundo gran objetivo del catálogo.

Investigación previa (antes de codear):

IntelliJ/WebStorm son Java/Swing, no Chromium — mañas distintas a VS Code.
El temido "gray box" del reparenting de Java es problema de Linux, no Windows → no aplicaba.
Riesgo real anticipado: recreación del peer/HWND al reparentar (como el Notepad), splash screen, y single-instance/launcher.
Groupy (referente comercial de la categoría) es cerrado y no documenta su técnica → confirmado que no hay atajo, hay que descubrir empíricamente. Ángulo de tesis: OneBlack documenta lo que la industria esconde.

Resultado — escenario optimista, mejor de lo esperado:

IntelliJ y WebStorm se adoptan limpio con la maquinaria genérica existente, sin código específico. Se encuadran, el teclado anda, renderizan perfecto.
NO necesitan --disable-gpu ni el latigazo de repintado que VS Code exigía — Swing no tiene la composición GPU de Chromium.
El peer/HWND no se recrea al reparentar (a diferencia del Notepad WinUI) — el SetParent prende y se queda.
Ventanas internas (panel de Run corriendo tests: 14 pasando) y modales (Settings) se comportan bien — el modal abre centrado por encima de OneBlack, que es lo correcto.

Hallazgo de tesis (contraintuitivo): Java/Swing (tecnología más vieja) resultó más fácil de reparentar que Chromium/WinUI (modernas). Las apps modernas con sus propios motores de composición son las difíciles; las tradicionales Win32/Swing se reparentan sin dramas. Refuerza el patrón: cada tecnología de UI tiene sus esquinas, y las modernas traen más.

Problema pendiente de producto — el cartel del launcher JetBrains:

Al abrir un proyecto con instancia existente, IntelliJ/WebStorm muestran "¿ventana actual o nueva?". Se resolvió cambiando la preferencia del IDE a "New window".
Pero esa config es del IDE del usuario, no de OneBlack → OneBlack no puede garantizarla en cualquier máquina. Anotado como pendiente de producto: manejar el cartel sin depender de la config del usuario (flag de lanzamiento específico de versión, o instancias separadas). No bloquea desarrollo.

Configuración de catálogo: IntelliJ y WebStorm agregados con ruta completa al .exe (no están en PATH), ArgumentosBase = "nosplash", usaCarpeta: true, NombreProceso = idea64 / webstorm64.

Estado: tres IDEs soportados (VS Code, IntelliJ, WebStorm). El objetivo del catálogo cumplido.

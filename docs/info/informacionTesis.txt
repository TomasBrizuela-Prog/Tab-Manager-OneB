Fase 0 — Setup y decisiones de arranque
Stack elegido: C#/.NET (WPF) para contenedor + core Win32, por P/Invoke de primera clase. Plugins en su terreno nativo (IntelliJ en JVM, VS Code en TypeScript). Core del reparenting es territorio del autor; el resto se delega a Claude.
Estructura: solución con cuatro proyectos — OneBlack.Contenedor (WPF), OneBlack.Core (Win32, del autor), OneBlack.Core.Tests (NUnit), OneBlack.Janitor (consola, watchdog). .NET 10, Visual Studio Community 2026.
Repo: git desde el día uno, remoto en GitHub personal privado; repo de facultad se sumará después como segundo remoto.
Método: spike antes que arquitectura; Claude entrega clases completas comentadas, el autor lee/valida/hace explain-back corto.
Fase 1 — Spike de reparenting (validación de la incógnita central)
Pregunta que abría el proyecto: ¿es posible embeber un IDE real en una ventana propia? Respondida: SÍ. Go/no-go = GO.
Modelo mental WPF clave: WPF dibuja sus controles en vez de crearlos como ventanas del sistema, así que no hay un HWND-hijo donde hospedar una ventana externa; HwndHost crea esa ventana real faltante y ahí se reparenta.
Clases del core construidas: VentanaAnfitriona : HwndHost (puente WPF↔Win32), AdoptadorDeVentanas (el músculo, maneja varias ventanas vía diccionario), EstadoOriginalVentana (guardar antes de tocar, restaurar al soltar).
Descubierto — el delegate del wndProc debe guardarse en un campo para que el GC no lo recolecte mientras Windows lo usa (bug clásico si se omite).
Descubierto — fondo sólido en la clase de ventana (hbrBackground negro) resuelve el "fantasma" que quedaba al devolver: el contenedor no se repintaba solo.
Secuencia de adopción (orden no casual): guardar estado → cambiar estilos (quitar WS_POPUP/WS_CAPTION/WS_THICKFRAME, poner WS_CHILD) → SetParent → SetWindowPos para encajar → registrar → persistir. Devolver es la inversa.
Validado con Notepad clásico: adopta (desaparece de la barra de tareas = reparenting genuino), sincroniza resize, devuelve intacto.
Fase 2 — Janitor / supervivencia ante crash
Construido: PersistenciaEstado (archivo ventanas-adoptadas.json con escritura atómica por temporal+renombre) y OneBlack.Janitor (proceso separado que duerme con WaitForSingleObject hasta que OneBlack muera y restaura las ventanas).
HALLAZGO CRÍTICO — el janitor reactivo pierde la carrera contra la muerte dura. Con kill duro (TerminateProcess), la ventana hija (WS_CHILD) muere en el mismo instante que OneBlack. El janitor llega rapidísimo pero después de que la ventana ya murió. Motivó el rediseño completo de la estrategia de supervivencia.
Restricción de fondo confirmada (Microsoft): una ventana tiene parent O owner, nunca ambos. WS_CHILD da confinamiento visual pero muere con el padre; owner da supervivencia pero no confina. No hay flag que dé las dos.
DECISIÓN CERRADA: priorizar confinamiento visual (WS_CHILD, es la identidad del producto) y garantizar no-pérdida de trabajo por persistencia de sesión, no por supervivencia de ventana. El insight: el objetivo correcto no es "que la ventana sobreviva" sino "que el trabajo del usuario sobreviva" (se reconstruye desde disco). Tres capas: cierre ordenado (hecho), manotazo por excepción (hecho pero frágil, no principal), persistencia de sesión (diseñada, pendiente de implementar).
Fase 3 — Enumeración, whitelist y adaptadores
Se pasó de FindWindow a EnumWindows (recorre todas las ventanas y filtra con lógica propia). Motivado por múltiples ventanas del mismo programa y por VS Code (clase de ventana genérica de Chromium Chrome_WidgetWin_1, compartida con Discord/Chrome — no sirve filtrar por clase).
Construido: BuscadorDeVentanas (enumera + filtra por visible/con título/en whitelist, identifica por nombre de proceso) y CatalogoDeProgramas (la whitelist; agregar un programa = una línea).
DECISIÓN — whitelist, no blacklist. Razones: identidad del producto, seguridad (nunca adopta ventanas del sistema por accidente), y calidad por programa (cada uno tiene sus mañas; soportar una lista conocida permite afinar y prometer que funciona). Excluye a la propia OneBlack automáticamente.
Fase 4 — Adopción de VS Code (Electron/Chromium)
HALLAZGO — ventana negra tras adoptar. VS Code se adoptaba a nivel Win32 pero no renderizaba (quedaba negro). Causa: la composición por GPU de Chromium — la superficie GPU queda huérfana al reparentar y Chromium no la recrea. Solución: lanzar VS Code con --disable-gpu (renderiza por software, sin superficie GPU que se rompa). Confirmó el modelo "OneBlack lanza los programas" con los flags correctos, en vez de "adoptar lo que el usuario ya abrió".
HALLAZGO — el teclado no llegaba a VS Code. Mouse funcionaba, teclado no. Es el problema más profundo del reparenting cross-proceso. Dos causas: (1) las colas de input de threads distintos se desacoplan al reparentar; (2) Chromium enruta el teclado a su vista interna según WM_ACTIVATE, que el reparenting rompe. Solución combinada: AttachThreadInput (acopla las colas de input; desacoplar SIEMPRE al devolver o rompe el foco de todo el sistema) + SendMessage(WM_ACTIVATE, WA_CLICKACTIVE) (despierta el enrutamiento interno de Chromium). Esta segunda pieza era la que faltaba.
Fase 5 — Selección de candidatas (UI) y correcciones del ciclo
UI de selección con ComboBox (Refrescar + Adoptar + Devolver) reemplazó los botones de prueba.
Corregido — cambio de pestaña: MostrarSolo(hwnd) muestra la elegida y oculta el resto (SW_SHOW/SW_HIDE).
Corregido — Devolver dejaba la ventana oculta: SW_SHOW al inicio de Devolver.
Corregido — refrescar rompía la adoptada: las adoptadas no aparecen en la enumeración (son hijas); se combinan libres + adoptadas recordadas preservando selección.
Corregido — escalado DPI (125%): WPF trabaja en unidades lógicas, Win32 en píxeles físicos. Helper DimensionesFisicas() multiplica por el factor de escala. Debe funcionar CON escalado, no pedir desactivarlo.
Fase 6 — Estabilización del ciclo adoptar/devolver (sesión más reciente)
RESUELTO — condición de carrera adoptar/devolver. Síntoma: adoptar+devolver rápido rompía; esperar unos segundos lo evitaba. Causa: los Dispatcher.BeginInvoke(Render) diferidos corrían después del Devolver, sobre una ventana ya restaurada. Intento fallido: reemplazar por UpdateLayout() síncrono (mató la carrera pero rompió el encaje). Solución: guardar la operación diferida en un campo (encajeDiferido) y cancelarla con .Abort() al inicio del Devolver si sigue pendiente.
RESUELTO — render negro en Chromium tras mostrar/adoptar. Dato clave: clickear o cambiar de pestaña no lo revivía. Causa: Chromium solo recompone su superficie ante WM_SIZE, no ante SW_SHOW ni WM_ACTIVATE. Solución: ForzarRepintado(hwnd) — latigazo de tamaño (1px y volver) + RedrawWindow con RDW_ALLCHILDREN. Se dispara en MostrarSolo y con reintentos espaciados (timer, 3×~120ms) tras adoptar. Race-safe.
HIPÓTESIS DESCARTADA — corrupción de WS_CHILD. Se creyó que WS_CHILD se propagaba entre ciclos. El fix (& ~WS_CHILD) empeoró el bug. Se instrumentó con logs de estilos en hex: probaron que los estilos se restauraban perfectos. Hipótesis falsa. Aprendizaje de método: instrumentar antes de teorizar; el fix a ciegas costó tiempo.
IDENTIFICADO — recreación espontánea del HWND (la causa real del "aleatorio"). Los logs mostraron el HWND del Notepad cambiando entre pruebas (2060C→30602). El Notepad de Windows 11 (WinUI) destruye y recrea sus ventanas solo. OneBlack operaba al devolver sobre un handle ya muerto → ventana fantasma. Prueba decisiva: Notepad quieto 30s → rompió igual (espontáneo, no por interacción); VS Code ciclado → siempre sano. Conclusión: no es bug de OneBlack, es un caso de prueba patológico. Los IDEs reales tienen HWND estables.
IMPLEMENTADO — salvaguarda IsWindow. Chequeo defensivo en Adoptar, Devolver (con helper LimpiarAdoptada), MostrarSolo, ReajustarTamaño, ForzarRepintado, DevolverTodas. No cura la recreación (imposible) pero evita operar sobre handles muertos y dejar basura. Aditivo: el camino feliz no cambia.
DECISIÓN — Notepad nuevo fuera del catálogo. Validado como no reparentable de forma confiable. Refuerza que la whitelist también garantiza "programa validado como reparentable", no solo seguridad.
Hallazgos de alcance (transversales, material de tesis)
Firma de código como requisito no-funcional de distribución. Smart App Control (WDAC) bloqueó la carga de OneBlack.Core.dll sin firmar (0x800711C7), de forma no-determinística (por reputación/heurística). Una app de reparenting es indistinguible de malware para los controles de Windows. La firma con certificado de editor verificado (EV, clave en hardware desde 2023) es obligatoria para distribuir a terceros — mismo requisito que productos comerciales como Groupy. Para la tesis: documentar la decisión (ADR) y opcionalmente demostrar el pipeline con certificado autofirmado. DECISIÓN DE FONDO ABIERTA — en análisis.
Identidad de ventanas en Win32 y límite de soportabilidad. El reparenting por HWND asume que el handle es estable durante la adopción; las apps WinUI lo violan recreando ventanas. Conclusión: el soporte de una app debe validarse por su estabilidad de ventana, no asumirse; y la mitigación correcta para el caso patológico es excluirlo y detectar la invalidación con gracia, no re-seguir la ventana. Saber dónde parar de robustecer es criterio de ingeniería.
Las apps modernas (Chromium, WinUI) reaccionan al reparenting de formas que las Win32 clásicas no. Patrón transversal: VS Code necesita --disable-gpu (render) y WM_SIZE (repintado); el Notepad WinUI recrea su HWND. El Notepad clásico (Win32 puro) nunca tuvo ninguno de estos problemas. Cada tecnología de UI tiene su propio conjunto de esquinas filosas.
